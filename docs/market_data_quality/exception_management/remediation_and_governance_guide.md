# M03.08 Remediation and Governance Guide

## 1. Remediation Workflows
Remediation in an institutional market-data pipeline must never involve direct in-place database updates. Instead, M03.08 manages remediation as a versioned, auditable, and traceable process:

```
[Finding Triggered] 
        │
        ▼
   [Quarantine] ──► [Investigation Notes] ──► [Correction Proposed]
        │                                              │
        │                                              ▼
        │                                    [Independent Approval]
        │                                              │
        ▼                                              ▼
[Rejected Record]                             [Idempotent Replay]
                                                       │
                                                       ▼
                                            [Validation Repass & Release]
```

---

## 2. Separation of Duties Policy
To maintain compliance with financial audit standards (such as SOC2 and BCBS 239):
- **Role Enforcement:** Analysts and operations staff (`OPERATOR`) can identify anomalies, add notes, and submit correction proposals.
- **Independent Approval:** Approvals must be granted by a separate authorized actor (`ADMIN` or Risk Supervisor).
- **Proposer Lockout:** The service layer programmatically verifies that `proposal.proposed_by != approver_id`. If violated, HTTP `403 FORBIDDEN` is returned and an audit warning is generated.

---

## 3. Provenance & Synthetic Data Isolation
Market data quality remediation differentiates between authentic market feeds and test environments:
- **Simulator Guard:** Synthetic data generated by local simulators carries `provenance_source = SYNTHETIC_SIM`. The engine prevents simulator records from ever being cited as authoritative evidence to alter `REAL` provider observations.
- **Financial Precision Preservation:** Before-and-after values are recorded as exact string representations (`before_value`, `after_value`) alongside explicit `field_data_type = DECIMAL` metadata, eliminating floating-point rounding errors.

---

## 4. Idempotent Replay Operations
When an approved correction is submitted for replay:
1. A deterministic idempotency key is generated from the exception reference, correction version, and replay mode.
2. The replay command is dispatched to M02's ingestion engine.
3. If an identical replay request is submitted again (e.g., during network retries or worker restarts), M03.08 returns the existing replay record rather than re-triggering ingestion.
4. Downstream validation and M03.07 use-eligibility evaluations are re-run on the reprocessed record.
